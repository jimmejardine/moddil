# The Website and Services: moddil.com

What the project serves from moddil.com, and what it deliberately does not.

## Summary

| Rule | One line |
|---|---|
| **Nothing on moddil.com is needed to build** | Every service is static files generated from public git repositories, so anyone can mirror it, and an outage never breaks a build ([Principle](#principle)). |
| **No accounts, no tracking** | There is nothing to log in to; no cookies, and no telemetry from the toolchain ([Principle](#principle)). |
| **One domain** | The site, the docs, the playground and the standard mods' names all live on moddil.com ([Services](#services)). |
| **No registry** | No naming authority, checksum database, proxy or download ranking ([What moddil.com does not run](#what-moddilcom-does-not-run)). |
| **The domain is part of the supply chain** | Standard mod names are URLs on moddil.com, so the domain is guarded like a signing key ([The domain is part of the supply chain](#the-domain-is-part-of-the-supply-chain)). |

## Problem

- A language needs a public home: a page that makes the case for it, a way to install it,
  documentation, a playground, and somewhere to publish security advisories.
- Most ecosystems grow a **central service that builds depend on**: crates.io, npm, PyPI and the Go
  module proxy and checksum database. Each is a single point of failure, an attack target and a
  naming authority. Moddil's packages have none
  ([`packages-and-supply-chain.md`: Hosting: plain git](packages-and-supply-chain.md#hosting-plain-git)),
  so the website must not bring one back through the side door.
- The services the specs need are scattered: vanity names, advisories, the playground, learning
  materials, toolchain downloads, ecosystem runs and dashboards. This document gathers them.

## Principle

**Decided:**

- **Nothing on moddil.com is needed to build.** Every service is a set of static files generated by
  CI from a public git repository, which stays the source of truth. Anyone can mirror the files,
  and an outage of the site never breaks a build: at worst it delays the first fetch of a standard
  mod, which a lockfile, a vendored copy or a local mirror already avoids
  ([`packages-and-supply-chain.md`: Local repositories and working copies](packages-and-supply-chain.md#local-repositories-and-working-copies)).
- **No accounts and no login.** The site holds no user data. There are no cookies; if traffic is
  counted at all, it is counted in aggregate, without cookies or fingerprinting.
- **The toolchain sends nothing.** It fetches from moddil.com only what the user asked for (a
  toolchain, a standard mod's redirect, an advisory feed listed by default) and reports no
  telemetry.

- **Every Run button** in the learning material, the reference and the standard mod docs opens the
  playground, because examples are tests
  ([`testing.md`: Examples are tests](testing.md#examples-are-tests)).
- **The playground needs cross-origin isolation** (COOP and COEP headers) for threads, so those
  headers are set on `/play` only; the rest of the site can embed and be embedded normally.
- **Mail:** `security@moddil.com` is the one address the project must keep, so it needs mail
  hosting with two-factor authentication.

## What moddil.com does not run

| Not run | Why |
|---|---|
| **A registry or naming authority** | A mod's name is its URL ([`packages-and-supply-chain.md`: Names are URLs](packages-and-supply-chain.md#names-are-urls)); no one has to ask the project for a name. |
| **A checksum database or module proxy** | The lockfile pins each dependency's commit, tree hash and signing key, so integrity needs no third party; teams that want a cache run an ordinary git mirror ([`packages-and-supply-chain.md`: Lockfile and vendoring](packages-and-supply-chain.md#lockfile-and-vendoring)). |
| **Download counts or rankings** | They reward popularity rather than quality, are easy to inflate, and need tracking. The popular-mods list is curated by hand. |
| **Accounts, publishing tokens or uploads** | Publishing is pushing a signed git tag to the mod's own repository ([`packages-and-supply-chain.md`: The source is the release](packages-and-supply-chain.md#the-source-is-the-release)). |
| **Toolchain telemetry** | Builds must not depend on, or report to, the network. |
| **A mod search engine, for now** | A pkg.go.dev-style index that renders docs for every public mod would be useful, but it is optional by construction and waits for an ecosystem. |

## The domain is part of the supply chain

**Decided.** Standard mod names are URLs on moddil.com, so whoever controls the domain controls
where a *new* fetch of `moddil.com/net` goes. Existing users are protected: their lockfiles pin
the commit, the tree hash and the signing key, and a changed key is flagged
([`packages-and-supply-chain.md`: Lockfile and vendoring](packages-and-supply-chain.md#lockfile-and-vendoring)).
New users are not, so the domain is guarded like a signing key:

- registrar lock, with renewal several years ahead;
- two-factor authentication on the registrar, DNS and mail accounts, held by more than one person;
- DNSSEC, and CAA records naming the certificate authorities allowed to issue for moddil.com;
- HTTPS only, with HSTS preloaded;
- the domain passes to the foundation when it exists
  ([`governance.md`: Funding](governance.md#funding)).

## Hosting

**Decided (November 2026):**

- **One origin, built by CI** from this repository and the repositories it renders (advisories,
  proposals), and deployed as a static site.
- **Cloudflare Pages.** The host must support headers per path (COOP and COEP on `/play`) and
  redirects; Cloudflare Pages reads them from `_headers` and `_redirects` files, has a global CDN
  and no bandwidth limit on its free tier. (Netlify works the same way; GitHub Pages does not set
  custom headers.)
- **Astro (Starlight) generates the site**: layout, navigation, search and the Markdown pages.
  `moddil doc`, once built, emits what only Moddil's own tool can: the mods' API pages, and code
  blocks that are type-checked (a broken example fails CI), linked to their definitions and given
  Run buttons into `/play`. Astro includes those fragments, so Moddil never rebuilds a generic site
  generator.
- **The site goes up with the playground**, once `/play` runs real programs: the first thing a
  visitor can do is run Moddil, rather than read a placeholder.
- **The release archives are mirrored** to GitHub Releases, so an install never depends on one host.
