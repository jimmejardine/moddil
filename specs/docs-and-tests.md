# Docs, Examples and Tests Next to the Code

> **Status:** decided direction, details open. Expands [`rationale.md`](rationale.md) §2.17 and §2.18,
> and gives the tools of [`correctness.md`](correctness.md) one place to live. Snippets are
> **illustration only**; no syntax is committed.

## 1. Summary

| Rule | One line |
|---|---|
| **Docs are checked** | `///` Markdown is parsed into the canonical AST. Parameter names, links and error docs are checked against the code. |
| **Overviews map the code** | Mod, module (`//!`) and declared-group overviews explain the big picture; required for every public module; every public item joins a group with `#[group(…)]`, and private items inherit the groups of the items that use them; checked links, cited evidence and a runnable tour keep them current. |
| **Docs are partly generated** | Effects, capabilities, the error set, contracts, traps and the assurance level are written by the compiler, so they never go stale. |
| **Examples are tests** | Examples carry expected results (`// => value`), compile in the same build, and run under the deterministic simulation runtime. |
| **Tests name what they test** | `test "…" for withdraw { }` sits next to its subject, with private access. Tooling knows every test's subject. |
| **Correctness tools attach the same way** | Property tests, fuzz targets, snapshots, interleaving tests, model-checking harnesses and proofs all attach to a subject. Contracts become tests automatically. |
| **Only affected tests run** | Test impact analysis plus results cached by content hash. |
| **Two audiences** | `///` is for users of an API; `note` is for maintainers (why). |
| **Benchmarks attach too** | `bench "…" for f { }`; performance deltas appear in semantic diffs. |

## 2. What Rust gets right, and where it stops

Rust gets a lot right: `///` Markdown docs, doc tests that compile and run, a `#[cfg(test)]` module in
the same file with access to private items, and one `cargo test`. Its limits:

- **Docs are unchecked prose.** A `# Errors` section can list errors the function no longer returns;
  parameter names drift; `# Panics` and `# Safety` exist by convention, enforced by lints at best.
- **Doc tests are compiled as separate crates.** They are slow (the 2024 edition merges them to
  help), cannot see private items, and perform real I/O.
- **Tests are not tied to what they test.** A test module is a bag of functions.
- **Every run re-runs everything**, unless outside tools (nextest, Bazel) are added.
- **Docs mix two audiences**: users of the API, and maintainers who need to know why.

## 3. The whole picture in one example

```
/// Withdraws `amount` from the account and returns the new balance.
///
/// # Parameters
/// - `account`: the account to debit.
/// - `amount`: how much to take; must be positive.
///
/// # Example
/// let mut acct = Account::open(100);
/// withdraw(&mut acct, 30)               // => 70
/// withdraw(&mut acct, 100)              // => fail(Overdraft)
note "Balances are integer cents; see [[ADR-12]] for why we don't use decimals here."
fn withdraw(account: &mut Account, amount: Money) -> Money with fail(Overdraft)
    requires amount > 0
    ensures  account.balance == old(account.balance) - amount
{ … }

test "rejects overdraft" for withdraw {
    let mut acct = Account::open(10);
    expect_fail(Overdraft, || withdraw(&mut acct, 20));
}

property "never goes negative" for withdraw (acct: Account, amount: Money) {
    try { withdraw(&mut acct, amount) } catch { _ => {} }
    assert(acct.balance >= 0);
}

bench "hot path" for withdraw { … }
```

The generated documentation for `withdraw` additionally shows: its effects and capabilities (none
beyond `fail`), its error set (`Overdraft`), its contracts, possible traps (none), the tests,
properties and benchmarks attached to it, its mutation score, and the mod's assurance level.

## 4. Docs are checked and partly generated

`///` stays, because it is familiar and LLM-friendly, but the compiler parses it into the canonical
AST (rationale §2.18) instead of treating it as a comment.

**Checked:**
- documented parameter names must exist, and (per mod policy) every parameter is documented;
- links such as `[[Account::open]]` must resolve. They point at *definitions*, so a rename updates
  them (rationale §2.19);
- a hand-written errors section must match the function's actual error set
  ([`error-handling.md`](error-handling.md) §5).

**Generated by the compiler**, never hand-written:
- effects and capabilities;
- the error set;
- contracts (`requires`, `ensures`, invariants; [`correctness.md`](correctness.md) §3.1);
- traps the function can raise (bounds, division, `unreachable`), or a proof that it raises none
  (assurance level L1, [`correctness.md`](correctness.md) §4.2);
- attached tests, properties and benchmarks, with mutation scores (§7).

**Coverage policy** is per mod and can follow its assurance level: for example, every public item
documented with at least one example at L1 and above.

### 4.1 Overviews: mod, module and group docs

Per-item docs say what one function does. What LLM-generated code most often lacks is the **big
picture**: what a module is for, how its pieces fit together, and where to start. Moddil treats docs
as a **map, read top-down** by humans and agents alike, with per-item text the exception rather than
the rule.

**Three scopes above individual items**, all parsed into the AST like `///`:

| Scope | Where | Answers |
|---|---|---|
| **Mod overview** | The mod's root module | What is this package for, and where do I start? |
| **Module overview** (`//!`) | The top of each module | What does this module do, what are its key concepts and invariants, which items are the entry points? |
| **Group** | A named theme declared once; items opt in with `#[group(…)]` | What do these functions do *together*? |

```
//! # Order matching
//! Matches incoming orders against the book in price-time priority.
//!
//! Concepts: [[OrderBook]], [[Level]], [[Fill]].   Start here: [[match_order]].
//! Invariant: the book never crosses ([[OrderBook::no_cross]]).
//!
//! let mut book = OrderBook::new();
//! book.add(bid(100, 5));
//! match_order(&mut book, ask(99, 3))      // => [Fill(99, 3)]     (the tour, run as a test)

/// Each side is a sorted list of levels; orders queue FIFO within a level.
group levels "Price levels"

/// How fills are computed and reported to the client.
group fills "Fills and reporting"

#[group(levels)]
pub struct Level { … }

#[group(levels, fills)]                // an item may belong to several groups
pub fn consume_level(…) { … }

fn remove_empty(…) { … }               // untagged private helper: inherits `levels` and `fills`
                                       // from its caller `consume_level`
```

**Groups:**
- A group is **declared once**, with a free-text title and its `///` doc. Items join it with
  `#[group(name)]`, and may belong to **several** groups. Members need not be next to each other, and
  tagging never re-indents code.
- Group names are **checked**: a misspelt name is a compile error with "did you mean?"; renaming a
  group is a refactor intent ([`semantic-vcs.md`](semantic-vcs.md)).
- **Scope:** groups are local to their module. A `pub group` declared at the mod root can be used by
  every module in the mod, for themes that span modules (e.g. *Authentication* across `session`,
  `tokens` and `oauth`).
- Alternatives considered: free-form string tags (typos silently create new groups, and the group's
  doc has no home), blocks (one group per item, contiguous members, re-indentation), region markers
  (positional and unchecked).

**Membership rules:**
- **Every public item belongs to at least one group**, by an explicit `#[group]`: functions, types and
  constants alike. A public item without one is a compile error.
- **Private items may be tagged explicitly.** An untagged private item **inherits** the groups of the
  items that use it, computed from the call and reference graph:
  - the union of its users' groups, transitively (helpers of helpers), as a fixed point through
    recursion;
  - a private function inherits from its callers; a private type or constant from the items that
    refer to it; a function used as a value (a callback) from the function that refers to it;
  - tests, examples and benchmarks don't count as users;
  - an explicit tag replaces inheritance;
  - a private item with no grouped user has no group (it is usually dead code, which the compiler
    already reports).
- **Inherited groups are never written in the source.** They are computed, shown in the reviewer view
  ([`agent-interface.md`](agent-interface.md) §5.1), and served by the language server and agent API
  ("part of *Price levels* and *Fills and reporting*, via `consume_level`"), so a human or an agent
  looking at any helper sees which themes it serves.

**Written by people (or agents):** only what cannot be computed: purpose, key concepts, invariants,
entry points, a short tour, and pitfalls.

**Generated by the compiler:** the member list, effects, capabilities, error sets, and which modules
this one uses and is used by. The documentation page for a module combines the two.

**Required for the public surface:**
- every mod, and every module with public items, must have an overview. A missing one is a compile
  error by default; a mod may relax this (e.g. for prototypes);
- every public item belongs to a group (above);
- private items never require their own docs; their group, explicit or inherited, explains them.

**Keeping overviews from drifting:**
1. **Checked links.** Links such as `[[match_order]]` must resolve and, from an overview, must point
   at public items. They target definitions, so renames update them.
2. **Cited evidence.** An invariant stated in prose links to the contract or test that enforces it
   (`[[OrderBook::no_cross]]`). If the evidence is removed, the link breaks the build.
3. **A runnable tour.** The overview's example is compiled and run like any other example (§5), so
   when the main flow changes, the overview fails until it is updated.
4. **No orphans.** Every public item names a group, so the overviews and groups remain a real map of
   the module.

## 5. Examples are tests

- An example line may end with `// => value` (or `// => fail(E)`) as its expected result, like
  Python's and Elixir's doctests and Go's `// Output:`. Larger values use snapshot-style expected
  output stored next to the example.
- Examples compile **in the same build** as the mod, so they are fast and can use private helpers.
- Examples run under the **deterministic simulation runtime** ([`determinism.md`](determinism.md)):
  an example that "fetches a URL" gets a simulated network, so docs never flake and never need the
  internet.
- When a signature changes, broken examples are compile errors immediately, not stale text.
- Every example has a **Run** button that opens it in the in-browser playground
  ([`toolchain.md`](toolchain.md) §11.1).

## 6. Attached tests

- `test "name" for subject { … }` sits next to its subject (like Zig's `test` blocks and Pyret's
  `where:` clauses) and can see private items in its module.
- Tests without a single subject are module-level `test "name" { … }` blocks; larger scenarios live in
  separate integration-test modules.
- **Tooling knows each test's subject**:
  - "which tests cover `withdraw`?" is a query;
  - the semantic diff (rationale §2.19) reports "**`withdraw` changed, but none of its tests did**",
    a sharp signal when reviewing agent-written changes.
- **Tests use effect handlers, not mocks.** The simulation runtime is the default: virtual time,
  seeded randomness, simulated network and filesystem. Fakes are scoped handlers
  ([`determinism.md`](determinism.md) §4), not global monkey-patching.
- Tests, examples, notes and benchmarks are **excluded from the mod's interface hash and from release
  artefacts**, so editing a test never rebuilds dependents ([`build-times.md`](build-times.md)).

## 7. Correctness tools in the same place

The tools of [`correctness.md`](correctness.md) attach to subjects in the same way, so a reader sees a
function's whole specification and evidence in one place:

| Block / mechanism | What it is | See |
|---|---|---|
| `property "…" for f` | Property-based test; generators derived from types, automatic shrinking | correctness §3.3 |
| **Contracts as implicit tests** | Every function with contracts gets an automatic property test: generate inputs satisfying `requires`, check `ensures` and invariants (Eiffel AutoTest). Listed in the docs. | correctness §3.3 |
| `fuzz "…" for f` | Coverage-guided fuzz target; failing inputs are saved as attached regression tests | correctness §3.4 |
| Snapshot expectations | For comptime expansions and generated code | correctness §3.4 |
| `test.interleavings "…" for f` | Explores task interleavings under the simulation runtime | correctness §3.7 |
| Model-checking harnesses, `proof` blocks | Bounded model checking and deductive proofs; erased from builds | correctness §4.1, §4.4 |
| **Mutation score per declaration** | How many deliberate bugs in `f` its tests catch: test *strength*, not just presence. Shown in docs and PR summaries. | correctness §3.5 |
| Miri-style mode | A test-runner mode that runs tests on the interpreter with extra checks | correctness §3.6 |

## 8. Test impact and caching

- Builds are content-addressed, and the compiler knows the call graph and every test's subject. So
  `moddil test` runs **only the tests whose inputs changed** ([`build-times.md`](build-times.md) §4).
- Results are **cached by hash**, locally or in a shared remote cache, and reused across machines and
  CI runs.
- Under the simulation runtime tests are deterministic, so a cached pass is trustworthy. Tests that
  use real effects are marked and re-run according to policy.
- For agents iterating dozens of times per task, this turns "run the tests" from minutes into
  seconds.

## 9. Maintainer notes

- `note "…"` (or a `note { … }` block) records **why**: design reasoning, rejected alternatives,
  linked issues and design records.
- Notes are attached to declarations in the AST, so they survive moves and renames, unlike comments.
- They are shown to maintainers, reviewers and agents, and kept out of user-facing API docs.
- This is the "intent" half of rationale §2.18; where *provenance* (human or agent, model version)
  lives is still open there.

## 10. Benchmarks

- `bench "…" for f { … }` attaches a benchmark to its subject (Criterion-style statistics).
- Results are recorded per build hash, so the semantic diff can report **performance deltas** for
  changed functions (rationale §2.19).
- Noise handling: repeated runs, confidence intervals, and dedicated or pinned machines for
  benchmarks that gate merges.

## 11. For agents and tools

- The compiler API serves the docs, examples, contracts, effects and attached tests of the **installed
  version** of each mod. Agents read exactly the API they compile against, which addresses
  hallucinated and outdated APIs (rationale §2.18).
- **Groups as context.** For any item, the agent API reports its groups, explicit or inherited
  (§4.1), so an agent editing a private helper knows which themes it serves.
- **Overviews first.** Asked to explain a mod, the agent API returns the mod overview, then module
  overviews, then groups, and drills down to individual items only on request (§4.1). Agents get the
  theme before the details, and fit within their context.
- The doc site, language server and agent API all come from the same front end (rationale §2.17).
- Editors can fold or show tests, notes and benchmarks around a declaration, giving a literate view
  of the code.

## 13. Open questions

- Syntax for attaching tests to methods, trait implementations and generic instantiations.
- Shared fixtures and test-only helpers: how they are declared and kept out of release builds.
- Default doc-coverage thresholds per assurance level.
- Where notes and provenance live: in the source, or in a sidecar keyed by definition ID?
- Benchmark stability on shared CI machines.
- Should the semantic diff flag a module whose public interface changed but whose overview wasn't
  edited?

## Background

Tooling uniformity (rationale §2.17), which this document builds on.

- **Lesson from Go and Rust.** One official formatter, test runner, doc generator, package manager,
  LSP, benchmark harness and linter, shipped with the compiler, removes endless ecosystem fragmentation.
- **Directions.** The compiler is a library and a service; every tool (formatter, LSP, agent API,
  semantic diff, docs) uses the same front end.
