# Modules, Visibility and Program Structure

## Summary

| Rule | One line |
|---|---|
| **The file tree is the module tree** | `src/book/levels.moddil` is module `book::levels`; there are no `mod foo;` declarations. |
| **Three visibility levels** | Private (this module), `pub(mod)` (any module in this mod), `pub` (exported from the mod). |
| **The mod boundary is where things become explicit** | `pub` items write full signatures, belong to groups and are semver-checked; everything else is inferred. |
| **Cycles inside a mod, a DAG between mods** | Modules of one mod may refer to each other freely; mods never form cycles. |
| **No glob imports, except preludes** | `use a::b::{c, d}`; `use x::*` only for a mod's declared `prelude`. |
| **Conditional code is comptime `if`** | Branches on `target` and `profile` are ordinary code, type-checked for every tier-1 target. |
| **No feature flags** | Optional functionality ships as separate mods. |
| **Library and executables** | The manifest names the library root and any executables. |

## Problem

- The **mod boundary** already carries a lot of meaning: explicit effects, capability ceilings,
  required groups and semver checks. But the module system inside a mod is undecided.
- **`#[cfg]` rot**: in Rust, code excluded by `#[cfg]` is never type-checked on the developer's
  machine, so platform code breaks silently.
- **Feature flags**: Cargo's additive features are unified across the whole dependency graph, so
  features get enabled behind a mod's back, and the number of combinations to test is 2^n.
- **Glob imports** make code non-local: a reader, or an agent, can't tell where a name comes from
  without looking elsewhere.
- **Visibility sprawl**: Rust code fills up with `pub(crate)`, and its five levels are more than
  most code needs.

## State of the art

| Topic | Rust | Go | Swift | Zig | Python / TypeScript |
|---|---|---|---|---|---|
| **Visibility** | Private, `pub(super)`, `pub(in path)`, `pub(crate)`, `pub` | Capitalised names are exported; everything is visible inside a package | `private`, `fileprivate`, `internal` (default), `public`, `open` | `pub` or file-private | Conventions (`_name`) / `export` |
| **Files and modules** | One file per module, each declared with `mod foo;` | A directory is a package; its files merge | Files merge into a module | A file is a struct-like namespace | The file tree is the module tree |
| **Cycles** | Allowed inside a crate, forbidden between crates | Forbidden between packages | Allowed inside a module | Allowed | Allowed (with runtime pitfalls) |
| **Conditional code** | `#[cfg(...)]`; excluded code is not checked | Build tags and `_linux.go` suffixes | `#if os(...)` | Ordinary `comptime if` on `builtin` | Runtime checks |
| **Optional parts** | Additive features, unified across the graph | Separate modules | Separate packages | Build options | Extras / optional peer dependencies |
| **Glob imports** | `use x::*` | Dot-imports, discouraged | Whole-module imports | `usingnamespace` (being removed) | `from x import *` / `export *` |

## Decisions

### Mods and modules

- A **mod** is the unit of distribution (a package); a **module** is a namespace and file unit inside
  a mod ([`requirements.md`](requirements.md)).
- **The file tree is the module tree.** `src/book/levels.moddil` is the module `book::levels`. There are
  no `mod foo;` declarations to keep in sync.
- **One file, one module** (decided): a file cannot contain further modules, so there are no inline
  `mod x { … }` blocks. The only exception is modules generated by comptime, declared **`mod name;`
  with a generating attribute** (decided), such as `#[c_import(header = "sqlite3.h")] mod sqlite3;`
  ([`interop.md`](interop.md)); a bare `mod name;` without one is an error. Tests are attached to
  declarations ([Conditional code is comptime `if`](#conditional-code-is-comptime-if)), so they need
  no inline `mod tests` either. Snippets elsewhere that show `mod api { … }` inline are
  illustrations of separate files.
- A file's `//!` doc comment is the module's overview
  ([`docs.md`: Overviews: mod, module and group docs](docs.md#overviews-mod-module-and-group-docs)).
- **Mods, modules and directories (decided).** One mod contains many modules: every file under its
  source tree. "The file tree is the module tree" only means that no file is declared by hand; it
  does not mean one artefact per directory. One mod produces at most one library and any number of
  executables ([Library and executables](#library-and-executables)).
- **A nested manifest starts a separate mod (decided).** A directory containing its own manifest is
  the root of another mod and is left out of the enclosing mod's module tree, as Go treats a nested
  `go.mod`. The enclosing mod may depend on it by relative path, as in a monorepo
  ([`packages-and-supply-chain.md`: Local repositories and working copies](packages-and-supply-chain.md#local-repositories-and-working-copies)).

### Three visibility levels

| Level | Written | Visible to | Signature |
|---|---|---|---|
| **Private** (default) | `fn f` | This module | Inferred |
| **Mod-wide** | `pub(mod) fn f` | Every module in this mod | Inferred |
| **Exported** | `pub fn f` | Every mod that depends on this one | Written out in full |

There is no `pub(super)` or `pub(in path)`: a mod is small enough that "this module" and "this mod"
cover real needs. The spelling `pub(mod)` is decided: it is Rust's `pub(crate)`, named after the mod, as the path
root `mod::` is ([Imports](#imports)).

### The mod boundary is where things become explicit

- A `pub` item **writes its full signature**: parameter and return types, effects, error sets and
  contracts ([`syntax.md`](syntax.md), [`effects-and-capabilities.md`](effects-and-capabilities.md)).
- A `pub` item **belongs to a group**
  ([`docs.md`: Overviews: mod, module and group docs](docs.md#overviews-mod-module-and-group-docs)).
- The `pub` items form the mod's **interface artefact**
  ([`build-times.md`](build-times.md)), and the **semver check** compares them between versions
  ([`packages-and-supply-chain.md`](packages-and-supply-chain.md)).
- **Private and `pub(mod)` items are inferred**: types, effects and error sets, so code inside a mod
  stays as light as a scripting language's.
- The **capability ceiling** applies to the whole mod.
- A `pub` item may not expose a type that is less visible than itself (no private types in public
  signatures).

### Cycles

- **Inside a mod, modules may refer to each other in cycles.** The compiler resolves names per
  declaration (query-based), so cycles cost nothing, and mutual recursion across files stays natural.
- **Between mods, cycles are forbidden**: mods form a DAG and build in parallel
  ([`build-times.md`](build-times.md)).

### Imports

```rust
use moddil::collections::{HashMap, OrderedMap};
use mod::book::levels::Level;
pub use mod::book::levels::Level as PriceLevel;      // re-export: a facade for users
use moddil::units::si::prelude::*                     // allowed: a declared prelude
```

- Imports name what they bring in.
- **A path starts at `mod`, `self`, `super`, a dependency, or a name in scope (decided).** `mod::`
  is the root module of the current mod, as in `use mod::book::levels::Level`. Moddil has mods,
  not crates, so Rust's `crate::` is not used, and `crate` is not a keyword; `mod::` matches
  `pub(mod)`, which means visible anywhere in this mod.
- **`pub use` re-exports** let a mod present a facade over its internal layout.
- **No glob imports**, with one exception: a mod may declare **one `prelude` module**, which can be
  imported with `*`. This keeps unit packs and similar vocabularies convenient
  ([`units.md`: Imports](units.md#imports)) while ordinary code stays local.

- **`self` in an import group (decided November 2026).** `use moddil::net::http::{self, Request}`
  imports the module the path names and some of its items; `{self as h}` renames it. `self` is
  named at most once in a group, and only in one ([`tour.md`: Gaps](tour.md#gaps-the-tour-exposed), 6).

### Conditional code is comptime `if`

```rust
fn open_socket() -> Socket with Net {
    if const target.os == Os::Linux {
        linux::open_with_io_uring()
    } else {
        portable::open()
    }
}
```

- Platform- and profile-specific code is a comptime `if`, **written `if const`** (decided, in Rust's
  `const` spelling), on the `target` and `profile` values ([`comptime.md`](comptime.md)), not an
  attribute that hides code. Only the taken branch is compiled.
- **`moddil check` type-checks every branch against every tier-1 target**
  ([`targets.md`: Target names and tiers](targets.md#target-names-and-tiers)), so platform code
  cannot rot unnoticed.
- Test-only code is written as attached tests ([`docs.md`](docs.md)), not
  `#[cfg(test)]` modules.
- **Platform-specific dependencies use the same predicate** (decided). The manifest declares them
  under a Moddil comptime expression over `target` and `profile`, parsed by the compiler, so the
  manifest and the code cannot drift:

  ```toml
  [when."target.os == Os::Windows".dependencies]
  "github.com/acme/win32" = "1.4"
  ```

  ```rust
  if const target.os == Os::Windows { win32::set_console_mode(…) }
  ```

  The lockfile records versions for every target, so it stays portable, but a build fetches only
  its own target's dependencies: a dead Windows-only dependency never blocks a Linux user.
  `moddil check --all-targets`, which authors and CI run, fetches everything.

### No feature flags

- There are **no Cargo-style features.** Optional functionality ships as **separate mods**, often in
  the same repository with path-prefixed tags (`acme/json` and `acme/json-serde`;
  [`packages-and-supply-chain.md`](packages-and-supply-chain.md)).
- This means:
  - **no feature unification**: nothing is switched on behind a mod's back;
  - **no 2^n test matrix**: each mod is built and tested one way;
  - **capability ceilings stay per mod**: an optional networking extension is its own mod with its
    own `Net` ceiling.

### Library and executables

- The manifest names the mod's **library root** (if any) and its **executables**, each with its own
  `main` ([`lifecycle.md`](lifecycle.md)). A mod has **at most one library** and any number of
  executables (decided).
- **Executables have their own dependencies and ceilings (decided).** An executable may list extra
  dependencies and a wider capability ceiling (a server's `NetRoot`, a CLI's argument parser). Neither
  leaks to mods that depend on the library, so a library's users never pull in what its binaries
  need, and the library's ceiling stays as narrow as its own code.

```toml
# manifest (illustration only)
[mod]
name = "github.com/acme/matcher"

[lib]
root = "src/lib.moddil"

[[exe]]
name = "matcher-server"
main = "src/bin/server.moddil"
capabilities = ["net"]                                  # the executable's own ceiling
dependencies = { "moddil.com/net/http" = "0.4" }        # not seen by users of the library

[[exe]]
name = "matcher-cli"
main = "src/bin/cli.moddil"
dependencies = { "github.com/acme/args" = "1.2" }
```

### The manifest

**Decided: the manifest is `moddil.toml`, in the mod's root directory, written in a subset of TOML**
(decided November 2026): `#` comments, `[table]` and `[[table]]` headers, and lines whose value is a
string or an inline table of strings, so it is read without a TOML library and is easy to edit by
tools. What it holds so far:

```toml
[mod]
name = "github.com/acme/matcher"
edition = "2027"

[lib]
root = "src/lib.moddil"            # the default, if the file exists

[[exe]]
name = "matcher-server"
main = "src/bin/server.moddil"     # a module of the mod's tree

[dependencies]
shapes = { path = "../shapes" }    # a local mod, by the name the code uses for it
```

- The mod's **source directory** is the directory of its library's root, or `src`; every
  `.moddil` file under it is a module, and the library root is the root module (`mod`).
- A dependency is named by the identifier the code uses as its first path segment (`shapes::Point`).
- Versions, registries, the lockfile, capability ceilings, targets, profiles and lint levels are
  added to the same file as they are built ([`packages-and-supply-chain.md`](packages-and-supply-chain.md),
  [`toolchain.md`: Configuration](toolchain.md#configuration)).
