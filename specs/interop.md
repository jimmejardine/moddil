# Interoperability with C and Rust

## Summary

| Rule | One line |
|---|---|
| **Two foreign worlds only** | The language supports the **C ABI** and **Rust**. C++ is reached through C shims, never through a C++ importer in the compiler. |
| **C, both directions, zero overhead** | Direct header import, layout-compatible types, C export with generated headers. |
| **The toolchain compiles C** | C dependencies are built hermetically and cross-compiled by a pinned clang/LLVM component, fetched on first use, as `zig cc` does. |
| **Overlays type the C surface** | Shared annotation overlays add ownership, nullability, error conventions, effects (including `blocking`), thread affinity and capabilities. |
| **Rust through a generated bridge** | Tooling reads a crate's API and generates a C-ABI shim plus Moddil bindings, mapping ownership, `Option`, `Result`, panics and futures. |
| **WASM components as the sandbox** | Untrusted or browser-bound C and Rust code can be linked as WASM components over WIT. |
| **Foreign code is visible** | Raw bindings are `unsafe`; using them needs the `ffi` capability, which shows in signatures, audits and semantic diffs. |
| **Shells call in; they are not imported** | Swift, Kotlin and TypeScript UI shells reach a Moddil core through bindings generated by `moddil bind`; browser APIs come from WebIDL. Neither widens what Moddil imports ([`ui.md`](ui.md)). |
| **Callbacks are entry points** | Code called from C must handle all errors (R3); nothing unwinds across the boundary. |

## Scope: why C and Rust only

C++ interop is the most expensive interop feature a language can take on: templates, overloading,
exceptions and compiler-specific ABIs. Swift and Carbon have each spent years on it. Moddil does not.

| Need | Typical form | Covered by |
|---|---|---|
| Exchange SDKs, FIX engines (HFT) | Often C++ only | A thin **C shim** ([C++ through C shims](#c-through-c-shims)) |
| Game physics engines | Mixed: some C (e.g. Box2D v3), some C++ | C APIs where they exist; shims otherwise; or compiled to WASM and linked as a component ([WASM components: the sandboxed path](#wasm-components-the-sandboxed-path)) |
| CUDA libraries, LLVM, SQLite, OpenSSL, DPDK, libpq | C APIs | Direct ([The C ABI, both directions](#the-c-abi-both-directions)) |
| Mobile platform APIs (web store) | iOS: Objective-C/Swift; Android: Java/Kotlin | Still C underneath: JNI is a C ABI, the Objective-C runtime has a C API, and Swift can export C functions (`@_cdecl`). Platform mods wrap them. |
| The Rust ecosystem, existing Rust code (Hashiverse) | Rust crates | The generated bridge ([Rust: the generated bridge](#rust-the-generated-bridge)) or components ([WASM components: the sandboxed path](#wasm-components-the-sandboxed-path)) |
| Python libraries for research glue (NumPy, pandas in an HFT backtest) | CPython | A mod, `moddil/python`, on CPython's C API: Python objects are opaque handles, calls go through the free-threading handoff ([`adoption.md`: Python first](adoption.md#python-first)), and the mod needs `ffi`. Calling Moddil *from* Python is the first binding target |

## The C ABI, both directions

- **Zero-overhead calls** in both directions: a call to C is a direct call with the platform C calling
  convention.
- **Layout-compatible types**: structs, unions, enums and fixed arrays can be declared with C layout
  (`#[repr(C)]`); variadic C functions can be called.
- **Direct header import** through libclang (as Zig's `@cImport`): types, functions, constants and
  simple macros become raw bindings automatically.
- **The toolchain compiles C.** C sources of a dependency are compiled by the toolchain's clang
  component, using the LLVM Moddil already ships ([`compiler.md`](compiler.md)):
  - fetched on first use: clang is a separate, pinned and hash-verified component of about
    50–80 MB, downloaded by the first build that needs C, so pure-Moddil users never pay for it;
    offline installers may include it;
  - hermetic and reproducible: declared inputs only, the same compiler on every machine ([Package management and supply-chain security](packages-and-supply-chain.md));
  - cross-compiled to every Moddil target, including WASM ([Cross-compilation and deployment](targets.md), R1);
  - run in the build sandbox like any other build step.

```rust
#[c_import(header = "sqlite3.h", overlay = "sqlite3.overlay")]   // raw bindings + overlay → typed API
mod sqlite3;
```

## Annotation overlays

C headers say nothing about ownership, nullability, errors, blocking or threads. **Overlays** add it,
and turn raw bindings into Moddil types:

| C fact | Overlay says | Moddil result |
|---|---|---|
| Who frees a returned pointer | owned / borrowed / linear | Owned: a Moddil type whose drop calls the C free function. Borrowed: a view. Linear: when freeing can fail (e.g. a close that reports errors). |
| Can a pointer be null | nullable | `Option<…>` ([`types.md`: Optional values and invalid states](types.md#optional-values-and-invalid-states)) |
| How errors are reported | errno, negative return, out-parameter | `fail(E)` with a typed error |
| Can the call block | `blocking` | The runtime moves the call off its workers to a blocking pool, so one slow C call can't stall the scheduler. Such calls are the one exception to promptly cancellable I/O ([`lifecycle.md`: Cancelling I/O: no "press Enter", no self-connect](lifecycle.md#cancelling-io-no-press-enter-no-self-connect)). |
| Thread requirements | thread-affine, not thread-safe | Pinned tasks; values that can't be sent are wrapped accordingly |
| What it touches | capabilities (`Fs`, `Net`, …) | Checked like Moddil code ([`packages-and-supply-chain.md`: What a mod is](packages-and-supply-chain.md#what-a-mod-is)) |

- Overlays live in a **shared repository**, versioned against library versions, like TypeScript's
  DefinitelyTyped, so each C library is annotated once for everyone. It accepts overlays by reviewed
  pull request.
- **Consumers pin overlay versions** in the lockfile and record reviews in their own audit trail,
  like any dependency ([`packages-and-supply-chain.md`](packages-and-supply-chain.md)). A project's
  local overlay takes precedence, and an overlay change that alters ownership or capabilities is
  flagged in semantic diffs.
- An overlay is reviewable code: a wrong overlay is a bug in a specific, auditable place.

## The safety boundary

- **Raw bindings are `unsafe`.** Safe wrappers are ordinary mods built on them.
- Any mod that uses foreign code declares the **`ffi` capability**. It appears in signatures, package
  audits and semantic diffs ([Package management and supply-chain security](packages-and-supply-chain.md), [Diffs, code review and version control](semantic-vcs.md)): "`foo` 1.5 now uses `ffi`" is flagged on
  upgrade.
- Faults in foreign code are traps (class 3; [`error-handling.md`](error-handling.md) D8).
- Foreign code is **outside record and replay** unless it is wrapped by effects; the recorder flags it
  ([`determinism.md`: Record and replay](determinism.md#record-and-replay), [`observability.md`: Flight recorder and replay](observability.md#flight-recorder-and-replay)).

## Callbacks into Moddil

- A Moddil function passed to C as a callback is an **entry point**
  ([`error-handling.md`: Entry points must handle everything (R3)](error-handling.md#entry-points-must-handle-everything-r3)): its failure set must be empty, so no Moddil error can
  escape into C.
- Nothing unwinds across the boundary in either direction.
- Borrowed data passed to a callback follows the ordinary borrow and view rules
  ([`memory.md`: Borrowing](memory.md#borrowing)–[`memory.md`: View types](memory.md#view-types)); a callback cannot keep it.

## Export

- Moddil functions and `#[repr(C)]` types can be **exported with the C ABI**, with a **generated header**.
- **A trap in an exported function does not end the host.** The call returns the result type's
  zero value (0, `false`, null, an all-zero struct), or the sentinel the function names with
  `#[export(on_trap = -1)]`, and C reads `moddil_trapped()` after the call for the exact answer,
  since a sentinel can also be a valid result. `#[export(status)]` keeps its `i32` status. *Why:* a
  library must not kill the program that loaded it.
- Moddil mods can also be exposed to Rust as a **generated crate** ([Rust: the generated bridge](#rust-the-generated-bridge), reverse direction).
- This is the adoption path: Moddil can be introduced inside existing C, C++ or Rust projects one
  module at a time ([Open Questions and Next Steps for Moddil](roadmap.md)).

## Rust: the generated bridge

Rust has **no stable ABI**: layouts, generics, trait objects and `Result` cannot cross a boundary
directly. Moddil therefore uses the approach of Mozilla's UniFFI, ICU4X's Diplomat and `cxx`:
**generate both sides of a C-ABI bridge from one description.** Rust's experimental interoperable
ABI (crABI) is tracked but not depended on.

- **Input:** the crate's public API, read from rustdoc's JSON output, plus light annotations where
  intent is ambiguous.
- **Output:** a small Rust **shim crate** of `extern "C"` functions, and **Moddil bindings** that look
  like a native mod.

| Rust | Moddil |
|---|---|
| Owned values, `Box<T>` | Owned values, dropped through the shim |
| `&T`, `&mut T` | `&T`, `&mut T` (second-class borrows, no lifetimes) |
| `Option<T>` | `Option<T>` |
| `Result<T, E>` | `fail(E)` |
| `String`, `Vec<T>`, slices | Owned Moddil equivalents (moved or copied) or borrowed views |
| `Arc<T>` | Opaque handle: Moddil's biased RC has a different layout |
| Trait objects | Opaque handles with generated methods |
| Generics | Explicit instantiations listed in the bridge description |
| Panics | Caught in the shim; become traps |
| `async fn`, `Future` | A bridge mod drives the future from a Moddil task, and the waker reschedules the task, so Rust async code suspends as an ordinary Moddil effect |

```rust
#[rust_import(crate = "hashiverse-lib", version = "1.4")]   // generates shim + bindings; the mod needs `ffi`
mod hashiverse;

let post = hashiverse::Post::decode(bytes)?;   // Result<Post, DecodeError> → fail(DecodeError)
```

- **rustdoc JSON is unstable**, so the generator supports a window of its format versions, with a
  small adapter per version. CI runs it against Rust stable and beta, so breakage shows
  six weeks early, and a project can pin its Rust toolchain in the bridge description.
- **Generics beyond explicit instantiations:** the bridge also instantiates every concrete use the
  Moddil side makes of a generic Rust item, found at build time. A Moddil type used as `T` inside
  Rust goes through generated vtables, for traits marked bridgeable.
- **crABI, if it stabilises,** becomes a second backend under the same bridge description, removing
  shim copies for `Option`, slices and strings; the C ABI remains the fallback.

## WASM components: the sandboxed path

- C and Rust code compiled to WASM can be linked as **components**, with interfaces in **WIT**, which
  Moddil maps to and from automatically ([R1](requirements.md#firm-requirements)). Rust has strong tooling for this
  (`wit-bindgen`).
- It costs copying at the boundary (the canonical ABI), so it isn't zero-copy.
- In return, the foreign code is **isolated**: it can reach only the capabilities it is given, as
  RLBox does for C libraries in Firefox.
- It is the natural path for **untrusted crates**, for plugins, and for the **browser**.

## C++ through C shims

- C++ libraries are wrapped by a thin `extern "C"` layer, written in C++, that exposes a C API.
  Moddil then imports that like any C library.
- C++ exceptions must not cross the shim: catch them and return error codes, which the overlay maps
  to `fail(E)`.
- A **shim generator** for a subset of C++ (plain classes, non-template functions, explicit
  instantiations) is optional tooling, not part of the language or compiler.

## As built (M3a)

The first slice of the C ABI (slice M3a; reference `interop.md`):
- **Imports:** hand-written `extern "C" { … }` blocks, with C's scalar types and raw pointers,
  in mods with the `unsafe` capability, called in `unsafe` blocks. Header import through
  libclang (`#[c_import]`) and annotation overlays come later.
- **C sources** are a mod's `[c]` table, compiled by the system's C compiler (MSVC, or `cc`),
  not yet by a fetched clang component; zlib is vendored in `examples/zlib`.
- **`#[repr(C)]` structs** cross behind pointers only. No variadic calls or callbacks yet (structs
  by value and callbacks came in M3c, below).
- **Exports:** `#[export]` functions, a generated header, and `moddil build --lib` for a shared
  library (`--static` for a static one). The generated Rust crate comes later.
- **Runners:** native code and the MIR interpreter (marshalling pointer arguments); not WASM.

## As built (M3c)

The C ABI's completions (slice M3c; reference `interop.md`):
- **Structs by value** (`ffi.types.2`): `#[repr(C)]` structs as C and `#[export]` functions'
  parameters and results, passed by each target's rules (Windows x64, SysV x86-64, AArch64
  including Apple's) from one classification, `moddil-ffi`'s `abi` module, which native code and
  the MIR interpreter's trampolines share.
- **Callbacks** (`type.fnptr.1`): `fn(A) -> R` types, Moddil functions given to C through C-ABI
  wrappers (native) or Cranelift-made C functions that call back into the interpreter, and
  `void *` user data.
- **C's memory** (`core.ptr.2`, `ffi.core.2`, `ffi.native.2`): null pointers, pointer
  arithmetic, casts, and C strings; the MIR interpreter reads and writes through C's pointers.
- **Not yet:** variadic functions, struct values in callbacks, calling a `fn` value from Moddil,
  and C strings or arrays given back to C on the interpreter other than as copies.

## Background

The problem and the state of the art that led to this design.

**Problem.** Nobody adopts a language that can't use existing code. Decades of C libraries, huge C++
codebases, and a growing Rust ecosystem must be reachable with low friction and low overhead.

**State of the art.**
- **C ABI**: the de facto lingua franca. Every language speaks it.
- **Zig**: `@cImport` reads C headers directly; `zig cc` is a drop-in C/C++ cross-compiler. This is the
  best-in-class C story.
- **Swift**: direct C++ interop (importing classes, templates in some cases) without wrappers.
- **Carbon**: designed explicitly as a C++ successor with bidirectional interop.
- **Rust**: `bindgen`, `cbindgen`, `cxx` (safe C++ bridge), `crubit` (Google's C++/Rust interop).
- **D**: `extern(C++)` with substantial C++ ABI support.
- **Mojo**: Python interop as a primary adoption strategy.

**What still hurts.**
- C headers carry no ownership, lifetime, nullability or thread-safety information; bindings must
  guess or annotate by hand.
- C++ interop is hard: templates, overloading, exceptions, ABI differences between compilers.
- **Rust has no stable ABI**; interop goes through `extern "C"`, losing generics, traits, and ownership.
- Each FFI boundary is a hole in safety guarantees.

## Open questions

- Whether a C++ shim generator is written at all, and whether it is a standard tool or a community
  one.

## Alternatives considered

- **Direct C++ interop**, a C++ importer in the compiler as Swift and Carbon have: templates,
  overloading, exceptions and compiler-specific ABIs make it the most expensive interop feature a
  language can take on, and both have spent years on it. Thin C shims reach the same libraries.
- **Depending on crABI**, Rust's experimental interoperable ABI: it is not stable. It can become a
  second backend under the same bridge description if it stabilises.

## Prior art

Zig `@cImport` and `zig cc`; Rust `bindgen`, `cbindgen`, `cxx` and `autocxx`; Mozilla UniFFI; ICU4X
Diplomat; Google crubit; the Rust crABI proposal; the WASM Component Model and `wit-bindgen`; RLBox;
Swift's C interop and `@_cdecl`; JNI; TypeScript DefinitelyTyped. Swift's and Carbon's C++ interop
are the paths deliberately not taken.
